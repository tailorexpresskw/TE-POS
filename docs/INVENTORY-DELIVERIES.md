# Customer-home deliveries through inventory

The POS connects to Storage Manage Method's existing Deliveries section. This is delivery from the invoice's branch to the customer's home, not a transfer to the Home Service branch. Stock requests, stock quantities, bag transfers, staff accounts and existing financial records are not changed by this connector.

## Reception workflow

Create a linked **delivery sub-invoice** from the original invoice using **Add delivery / extra charge**, with Charge type set to **Delivery**. The printed document is labeled Delivery invoice. On that sub-invoice, choose **Send delivery request**. Enter the delivery area, full address, customer phone and name; optionally enter date, Kuwait ready time and a dispatch note. The branch is fixed to the original invoice. The request sent to inventory carries the delivery sub-invoice number.

**Save delivery draft** keeps the details only in POS. It does not create a New request in inventory, notify drivers or enter the inventory queue. Staff can prepare drafts while tailoring is in progress. Once Reception has checked every active service, Reception or Admin can click **Send delivery request**. That button records delivery approval and queues the request automatically as **Ready**, so dispatch/driver visibility follows the inventory app's existing permissions. Managers, Supervisors and Tailors cannot substitute for Reception's delivery approval.

The source branch, customer address and phone are shown together before sending. One persistent request links the original invoice to its selected delivery sub-invoice; retries do not create duplicates. The delivery sub-invoice must belong to that invoice and branch, be marked Delivery and not be cancelled or fully refunded. Generic extra-charge documents cannot be used to dispatch. The request does not collect another payment or add another fee. Its dispatch quote comes from the inventory area; the customer's separately billed delivery amount remains on the linked invoice.

Driver assignment, ETA, pickup and delivered status remain in inventory and synchronize back to POS. There is no second Mark ready step after Send. Delivery status stays separate from tailoring approval and financial status. Cancelling an unsent draft is local only. Cancelling/refunding the delivery invoice or original invoice withdraws pending dispatch; a driver already in transit requires coordination with dispatch. Existing sent history is preserved. Drafts cannot be reopened after cancellation.

If a backjob reopens work before dispatch, approval is withdrawn and Reception must check and send again. Previously submitted inventory history remains visible, but pickup is blocked while on hold. Synchronization between servers is asynchronous; check dispatch before physical handover.

Aventura is restored as an active POS branch using its original ID `aventura` and code `AV`. Existing records and staff assignments are preserved. Admin must map it to the matching inventory branch; if that branch does not yet exist in inventory, create it through inventory's existing Admin branch screen first. Similar names such as Al Hamra are not automatically renamed or mapped.

## Deploy both sides

1. The inventory repository needs `pos-deliveries.cjs` plus the prepared changes to `server.js` and `public/index.html`. Reviewable diffs are in `integrations/inventory/`. They add authenticated integration routes, serialize JSON mutation handlers and prevent linked deliveries bypassing POS readiness or being deleted. Existing ordinary inventory deliveries keep their workflow. Cancelled linked requests appear in delivery history and disappear from active driver queues.
2. Generate server configuration locally: `node scripts/setup-inventory-connection.mjs https://storage-app-sorj.onrender.com`. It saves matching private values under ignored `data/inventory-connection/`; it does not print the key, modify staff passwords or deploy either app. Re-running keeps the same key.
3. On the inventory Render service, set `POS_INTEGRATION_KEY` to the private value from `INVENTORY.env`. Deploy the inventory source changes. Keep its existing persistent `DATA_FILE` configuration and run one inventory process/instance per JSON file.
4. On the POS Render service, set `INVENTORY_URL=https://storage-app-sorj.onrender.com` and `INVENTORY_INTEGRATION_KEY` from `POS.env`. Deploy the POS source and compiled web assets. Keep the POS persistent disk and database. Keep migrations `0008_customer_deliveries.sql` and `0009_reception_delivery_approval.sql`. The latter adds delivery-invoice and approval fields, holds unsent requests locally for approval, and restores Aventura. It does not create inventory requests for historical invoices.
5. Sign in as POS Admin, open **Administration → Inventory delivery connection**, verify connection status and explicitly map each POS branch to the corresponding inventory branch. Each inventory branch can be selected only once. Missing mappings block requests. IDs are matched by approved mapping, never guessed from similar branch names. Existing requests retain their saved original source even if the mapping later changes.
6. Inventory needs active delivery areas and prices. Choose one small test order, create the delivery sub-invoice and save a draft. Confirm nothing appears in inventory. Complete reception review, click Send delivery request, then verify its Ready entry and try driver pickup/ETA/delivery. Local automated checks use synthetic data; they do not create live Render deliveries.

Local source preparation: `python scripts/prepare-inventory-adapter.py "C:\Users\user\storage-app-backend"`. It writes tested candidates to ignored `work/inventory-integration/` and checks the source shape. `scripts/apply-inventory-adapter.ps1 -InventoryRoot "C:\Users\user\storage-app-backend"` checks source hashes, backs up the two existing source files under private POS data and copies only those source changes plus the connector module. It does not stage, commit, push or modify inventory `data.json`.

## Connection behavior and checks

Keys stay on the servers. Flutter receives connection status, branch names, delivery areas and invoice-authorized delivery details, never the shared key. Requests follow normal POS role, assigned-branch and enabled shift restrictions. The inventory integration key permits only the new delivery/catalogue routes, not stock administration. It does not replace or redesign the inventory app's existing staff-login security model.

The connector sends only dispatch details: source IDs/branch, invoice number, customer contact/address, area and quoted charge, requested date/time and explicit delivery note. It does not send service measurements, internal backjob fault notes, staff passwords or the invoice's full financial history. Device-push messages remain generic.

The SQLite queue records synchronization status, attempts and safe error messages. Transient failures retry with backoff. Price/source/state conflicts require review, editing or Retry synchronization; a customer request is not discarded. Requests and driver-status updates use monotonic revisions. Inventory adapter protocol version 2 rejects first-time delivery creation without approval metadata. Integration status is visible per invoice, including reversed original invoices, and is branch-authorized. The outbox used by other workflows remains available for later inventory consumption or home-service integrations; this release only connects customer delivery.

Run `node --experimental-strip-types --test server/deliveries.test.mjs` and Flutter's `test/deliveries_test.dart`. To test a prepared copy of the actual inventory server with isolated synthetic data, run `node --experimental-strip-types scripts/inventory-adapter-smoke.mjs "C:\Users\user\storage-app-backend"` after preparation. These checks cover source branch, duplicates, lost responses, reception readiness, driver updates, JSON write preservation, cancellation, price conflicts, mapping permissions and phone/desktop screens.

After the adapter is installed and temporary preparation files are removed, the smoke command can test the applied inventory source directly with its own synthetic data file. Do not run preparation again against an already modified source tree.
